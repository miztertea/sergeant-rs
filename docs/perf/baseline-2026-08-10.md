# Performance Baseline — 2026-08-10

First measured baseline of the P0 prototype, per the
[P1-PERF contract](../gauntlet/contracts/P1-PERF.md). Every number below was
produced by the committed harness (`scripts/perf/`), run at full contract
scale, and every anomaly was independently reproduced by a second agent
before being accepted (one claimed finding was refuted and is noted).
Raw CSV/JSON lives outside the tree; this document is the distilled record.

**Unit under test:** `target/release/sgt` at `499c061`.
**Environment:** 4 cores (cgroup v1, no CPU quota), 15.7 GiB RAM, Intel Xeon
2.10GHz, Linux 6.18.5, loopback HTTP, fake backend (§37) except where noted.
Numbers from this container class are comparable to each other; treat them
as relative baselines, not absolute hardware claims.

## Idle profile

| metric | value |
|---|---|
| RSS (25 s sample, flat) | 28.6 MB, zero drift |
| fds / threads | 15 / 9 |
| CPU over settle window | 0.000 s |
| cold start, empty data dir | ~0.5–1.3 s (run-to-run variance ~2×) |

## S1 — burst submissions (concurrent `POST /v1/work`, complete 2-stage workflow)

| burst | wall | throughput | p50 | p95 | max | RSS peak | fds peak |
|---|---|---|---|---|---|---|---|
| 1 | 0.06 s | 17/s | 37.9 ms | — | 37.9 ms | 28.6 MB | 15 |
| 5 | 0.16 s | 31.8/s | 80.9 ms | 128 ms | 134 ms | 29.3 MB | 19 |
| 10 | 0.35 s | 28.8/s | 169 ms | 302 ms | 321 ms | 29.9 MB | 28 |
| 20 | 0.56 s | 35.6/s | 251 ms | 486 ms | 499 ms | 30.6 MB | 35 |
| 50 | 1.33 s | 37.6/s | 619 ms | 1101 ms | 1131 ms | 32.7 MB | 62 |

All works completed and were confirmed from the projection at every cell;
threads constant at 9; fds return to 15 after every burst; exactly 16
journal events per work. **Throughput plateaus at ~28–39 works/s regardless
of concurrency** — per-call p50 grows linearly with burst size; the daemon's
single-writer path saturates, not the client fan-out (curl-vs-harness time
gap ~0.8% at b50). This resolves the contract's Unknown #2: the daemon
saturates first. Filed as a tracked observation (architecturally expected
under the single-writer journal invariant, but now it has a number).

## S2 — sustained churn, 200 works in waves of 10, 120 s settle

| metric | value |
|---|---|
| submit phase wall (20 waves) | 6.25 s |
| RSS pre → peak → post-settle | 28.8 → 33.9 → **33.9 MB (zero reclaim)** |
| RSS per completed work | ~25 kB, strictly monotonic (slope +21 kB/work) |
| fds pre/peak/post | 15 / 24 / 15 |
| daemon CPU per work | 2.7 ms |
| journal growth | 547 B/event (16 events/work) |
| DuckDB growth | 2621 B/work (visible only after clean shutdown — see note) |

**Finding (major, filed):** RSS never declines after works reach terminal
state — the in-memory projection retains completed-work state with no
eviction, and 120 s idle reclaims nothing. ~25 kB/work is small, but it is
unbounded and now measured. Note: the DuckDB file only reaches disk at
clean shutdown; mid-run size samples read stale (harness issue filed).

## S3 — deep work (1,010 events on one work) + graph read load

| metric | value |
|---|---|
| graph response at depth | 3.0 kB (9 nodes / 8 edges) |
| sequential 100× graph reads | p50 9.7 ms, p95 13.7 ms |
| 20-way concurrent ×5 rounds | p50 42.6 ms, p95 60.9 ms (~4.4× p50 amplification) |
| round wall (20 reqs) | ~0.10 s — aggregate throughput does not collapse |
| RSS before/peak/after read burst | 36.3 → 65.0 → 49.5 MB (+13 MB retained, single-sample) |
| fds | 15 / 17 / 15 |

The p50 amplification is queueing under 5× core oversubscription, not
throughput loss (observation filed); the retained-RSS single sample needs a
repeat-trend before it's called a leak (observation filed with that framing).

## S4 — SSE fan-out: 25 subscribers through a 20-work burst

Exactly 1 fd per subscriber (15 → 40); all 25 subscribers saw every
terminal event; killing 10 subscribers mid-burst wedged nothing (20/20
HTTP 201, survivors saw all events); fds returned exactly to idle after
disconnect. A claimed ~35% submit-latency rise with subscribers attached
was **refuted** on reproduction (within run-to-run noise).

## S5 — journal scale: cold-start rebuild + analytics

| mark | cold start | rebuild rate (raw) | RSS after start | journal size |
|---|---|---|---|---|
| 10k events | 0.68 s | 14.6k ev/s | 69 MB | 5.5 MB |
| 25k events | 0.98 s | 25.8k ev/s | 113 MB | 13.8 MB |
| 50k events | 1.71 s | 29.2k ev/s | 178 MB | 27.4 MB |

The M5 ledger's ~15k events/s rebuild figure **holds with growing margin**
(fixed ~425–450 ms startup overhead dominates small journals). Canned
analytics queries: 7–20 ms warm at every mark, flat — except
`blocked_time_per_work`, whose *cold* call scales with event count
(153 → 495 → 792 ms at 10k/25k/50k; filed). Journal segments roll at
~8.4 MB; ~549 B/event steady. Live-incremental RSS at ~50k events
(139 MB) is notably lower than rebuild-from-scratch RSS at the same mark
(178 MB). DuckDB on-disk reached 31.8 MiB after clean shutdown at 50k.

## S6 — kill -9 mid-burst recovery, ×3 cycles

Across 3 cycles with 10 concurrent submits in flight at kill time: **zero
silently lost works, zero illegal states, zero duplicate executions, zero
orphan processes**; second restart byte-identical (idempotent); doctor
healthy; 0 unparseable journal lines. The command-ID crash-window index
was positively confirmed: an ambiguous no-HTTP-answer submit retried by the
client produced one work, not two. One new L6-class observation (filed):
a work can reach `work.completed` with its trailing `surface.torn_down` +
`command.accepted` events lost to the crash window — state legal, audit
trail not 1:1.

## S7 — client hygiene under load

| metric | value |
|---|---|
| TUI idle CPU (30 s, live SSE) | 0.03% — no busy render loop |
| TUI RSS | 13.0 MB idle, +0.6 MB through a 20-work burst |
| daemon fds with TUI attached | 15 → 17 → 15 after quit |
| `q` exit | 209 ms, terminal restored |
| dashboard under burst | 200s throughout; work page 271 ms mid-burst → 7.6 ms after |
| `sgt status` / `sgt web` | ~5–6 ms under load |
| `sgt doctor` | **~450 ms floor**, load-independent (subprocess probes; observation filed) |

**Finding (critical, filed):** a TUI orphaned from its pty (terminal
destroyed) survives, ignores SIGTERM (handler installed but shutdown parks
in `reader.join()` while the reader thread spins on the defunct pty fd at
~80% of a core), and requires SIGKILL. Reproduced 3/3 in smoke and again
at full scale and by the verifier.

## Disposition

22 findings raised → 21 confirmed on independent reproduction, 1 refuted.
Deduplicated to the GitHub issues listed in GAUNTLET.md's P1-PERF ledger
entry (the empty `surfaces/<work-id>/` directory leak recurred in every
scenario and is one issue). Nothing was fixed in this phase by design.
