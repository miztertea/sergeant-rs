# §8.6 — How a gate Work binds to the branch it reviews

Investigation, not implementation. Answers the open question ADR 0005 and
`reference/proposal-foundation-rationalization.md` §8.6 carry forward from
FOUNDATION-1's surviving error, `inv-one-owner-relocated`
(`docs/gauntlet/runs/foundation-1/critics/invariants.md` finding 1,
confirmed unchanged at error severity by
`docs/gauntlet/runs/foundation-1/refuters/invariants.md`). Does not
re-litigate ADR 0005's ruling that gating becomes a dispatched Work — that
is settled. This asks only how the gate Work reaches the branch it needs to
review.

## What was verified, and how

### 1. `src/runtime/surface.rs` has no path that binds a surface to a branch it did not mint

Read in full (1384 lines). Confirmed mechanically:

- `materialize` → `materialize_one` (`:373`) → `add_worktree` (`:636`) →
  `add_worktree_from(..., create_branch: true)` (`:642`), which always runs
  `git worktree add -b <branch> <path> <start>` where
  `branch = work_branch(work_id) = "sergeant/{work_id}"` (`:87-90`). There is
  no parameter anywhere on `materialize`, `SurfacePlan::new`, or
  `materialize_one` that accepts an externally supplied branch name.
- `rematerialize` (`:438`) re-attaches strictly to `binding.work_branch`,
  which was set at the surface's own `materialize` time and never changes.
- `teardown` (`:497`) "retain[s] every branch" (comment at `:17`,
  code at `:513` calling `teardown_binding`, which never deletes a ref) but
  never rebinds one to a different surface.
- `RepositoryBinding.work_branch` is a plain `String` field — nothing in the
  *type* forces it to equal `work_branch(work_id)` — but every current
  producer of a `RepositoryBinding` (`materialize_one`) fills it from that
  function. The data model has room for a binding whose `work_branch` names
  someone else's branch; no code path constructs one.

This matches the critic's and refuter's reading exactly. I did not find an
escape hatch either of them missed.

### 2. Git's worktree-branch exclusivity, reproduced directly (not trusted from the refuter's summary)

Ran fresh, three scratch repos under `/var/tmp` (`/var/tmp/gate-branch-test{,2,3}`, all now cleaned up conceptually but left on disk — not part of this repo). Commands and results:

```
$ git worktree add ../wt1 feature       # succeeds
$ git worktree add ../wt2 feature       # fatal: 'feature' is already used by worktree at '.../wt1'  (exit 128)
```

Confirms the refuter's finding. Two additional facts the critic/refuter did
not test, both load-bearing for the recommendation below:

**`--force` bypasses the exclusivity check, not just the dirty-removal check.** `git worktree add --force ../wt2f feature` *succeeds* while `../wt1` is
still attached to `feature` — git will happily check out one branch into two
worktrees at once if told to. `git worktree list` then shows both. This is
a real, working path, but it is exactly the footgun git's default refusal
exists to prevent: two live working trees sharing one branch ref have no
mechanism keeping their indexes/HEADs in sync, and I found no evidence
sergeant or no-mistakes reasons about that state anywhere. I am treating
this as a rejected variant, not a recommended one (see Mechanism A′ below).

**A clean `git worktree remove` fully frees the branch for an ordinary (non-forced) `git worktree add`.** After `git worktree remove ../wt1` (clean,
no dirty content), a plain `git worktree add ../wt3 feature` succeeds with
no special flags. This is the mechanism the recommendation below relies on.

**A dirty/retained worktree still blocks it**, exactly as sergeant's own
`teardown_binding_locked` would leave it: if the original worktree has
uncommitted content, `git worktree remove` itself refuses
(`fatal: '...' contains modified or untracked files, use --force to delete
it`), and — because sergeant's teardown never forces past that (`RetainedDirty`, `src/runtime/surface.rs:177-180`) — the worktree stays
registered and a second `git worktree add` on that branch still fails.
Reproduced directly.

**A detached checkout of the branch's tip coexists fine alongside a live worktree on that branch** — `git worktree add --detach <path> <branch>` does
not hit the exclusivity check at all, because it never attaches the branch
ref to the new worktree (`git symbolic-ref -q HEAD` in it exits 1, "not
currently on any branch"). This means a detached copy is cheap to create at
any time, but anything committed inside it never moves the branch it was
cut from — it is a dead end for a gate that needs its fixes to land on the
branch, not a way around exclusivity for anything that writes.

### 3. Teardown's sequencing relative to a Work's own lifecycle

`Engine::retire_run` (`src/runtime/engine.rs:1881-1900`), doc comment
verified directly: "the Work state change has already been journaled by the
caller, *then* the stage is marked, *then* the backend is asked to stop,
*then* the surface is torn down." So a Work's surface is torn down only
once that Work has reached a terminal state — not before, and not as part
of some other Work's processing. `teardown` (`surface.rs:497`) removes each
binding's worktree (or retains it, fail-closed, per the disposition rules
in `teardown_binding_locked`, `:568-634`) and always keeps the branch.

This matters directly for Mechanism A: the precondition "the target Work's
worktree is gone so its branch is free" is not a bespoke constraint someone
would have to invent — it is already how every Work ends. The open question
is not "can we ever get the worktree out of the way," it's "does the gate
Work's dispatch happen after that has already occurred, and what happens if
it hasn't."

### 4. No-mistakes' custody model, read from the actual stage contexts and `scripts/gate.sh`, not summarized

- `scripts/gate.sh:36`: `[ -z "$(git -C "$REPO_ROOT" status --porcelain)" ] || exit 1` — `REPO_ROOT` is resolved from the script's own location
  (`SCRIPT_DIR/..`), i.e., wherever it is invoked from. No-mistakes has no
  concept of "the branch to review" as a name passed in; its unit of
  operation is *whatever checkout it is run against*. It requires that
  checkout to be clean at the start, then takes ownership of it.
- `.sergeant/workflows/validate-and-ship/40-drive-gates/CONTEXT.md`
  (`BU-P1-076`): "While a run is active: do not edit the pipeline-owned
  worktree ... preserve all pipeline-created commits." The pipeline commits
  fix-round changes onto whatever branch is checked out in that worktree.
- `.sergeant/workflows/validate-and-ship/50-reconcile-custody/CONTEXT.md`
  (`BU-P2-092`, `BU-P2-090`): `axi sync --recover` "fast-forward[s] to the
  preserved head" — a local, in-checkout, in-branch operation. It has no
  parameter for "which branch elsewhere should receive these commits"; it
  moves the ref that is already checked out in that worktree.

Together these confirm the refuter's severity argument independently: the
custody model assumes the checkout no-mistakes runs against *is* the
checkout of the branch that will ship. Anything else requires a
reconciliation step (merge/rebase/cherry-pick from a copy back onto the
real branch) that neither `scripts/gate.sh` nor the `50-reconcile-custody`
stage contract describes or has authority to invent (`docs/DEVELOPMENT.md`
§50: "never improvise a reset, stash, force-push, or branch replacement").

### 5. No existing linkage lets one Work name another Work's branch

Grepped `src/domain/work.rs` for anything like `target_work`, `parent_work`,
`depends_on`: none exists. `Engine::plan`/`Engine::start`
(`src/runtime/engine.rs:963-1037`, `:1343-1412`) build a `SurfacePlan` from
`(surfaces_root, work_id, repositories)` only — there is no submission-level
field today that could carry "attach to `sergeant/<other-work-id>`'s
branch instead of minting your own." This is plumbing that does not exist
yet, not a hidden capability.

## Mechanisms considered

### Mechanism A — sequenced branch takeover (recommended)

Dispatch the gate Work only after the target Work has reached a terminal
state *and* its surface torn down clean (every binding `Removed`, not
`RetainedDirty`/`RetainedError`/`Missing`). At that point the branch
`sergeant/<target-work-id>` has zero worktrees attached to it in the source
repository (verified §2 above), so the gate Work's own materialization can
attach a fresh worktree to that *existing* branch with an ordinary
(non-forced) `git worktree add <path> <branch>` — mechanically the same
`add_worktree_from(..., create_branch: false)` call `rematerialize` already
uses (`surface.rs:469-475`), just invoked from a new caller with an
externally-supplied branch name instead of a freshly recorded one.

No-mistakes then runs against a worktree that *is* the real branch's
checkout. Fix commits land on `sergeant/<target-work-id>` directly;
`axi sync --recover` reconciles within that same checkout exactly as
`50-reconcile-custody` already assumes. No copy, no reconciliation step
that doesn't already exist.

**Cost / what it requires changing:**
- A `SurfacePlan`/`materialize` variant (or a new function alongside them)
  that takes an explicit branch name to attach to, rather than always
  deriving one from `work_branch(work_id)`. `add_worktree_from`'s
  `create_branch: false` arm already does the git-level work; what's
  missing is a public entry point and a `RepositoryBinding`/`SurfacePlan`
  shape that records "this branch was *attached*, not *cut*" (today's
  `base_branch`/`base_sha` fields describe cutting a new branch from a
  base — reusing them to also mean "the branch I attached to" would blur a
  provenance distinction the journal currently makes cleanly).
- A precondition check, run before materialization is attempted: is the
  target Work terminal, and did its surface teardown report `clean: true`?
  If not, the gate dispatch must fail closed (§4.3's invariant) rather than
  race the target Work's own teardown or silently hit git's refusal.
  Nothing in the current engine computes or exposes this check today; it
  would need to read the target Work's own journaled `surface.torn_down`
  event (`KIND_SURFACE_TORN_DOWN`, `surface.rs:85`) and its per-binding
  dispositions.
  - **What happens on a dirty/retained target teardown is undecided by this investigation.** Options include: block gate dispatch entirely until a human/Captain resolves the retained worktree, or route it back through the target Work's own retry path (`§12`'s "one door back out of failed/blocked/waiting", `surface.rs:894`). Neither is designed here.
- Submission-level plumbing: something in `SubmitContext`/`StartPlan`
  needs to carry "this Work reviews `<target-work-id>`'s branch" from
  wherever the gate Work is dispatched (Captain, per ADR 0005) down to
  `Engine::plan`/`Engine::start`. No such field exists today (§5 above).
- The gate Work's own `RepositoryBinding.base_branch`/`base_sha` should
  probably record the *target's* base (what the target Work itself was cut
  from), not "main" as of gate-dispatch time and not the target's branch
  name — otherwise `work show` on the gate Work reports confusing
  provenance. Not designed here; flagged as a real modeling question.

**Sizing:** touches `src/runtime/surface.rs` (new/extended materialize
path), `src/runtime/engine.rs` (new precondition check, new plumbing
through `plan`/`start`), and whatever submission surface (CLI/API) is
chosen to carry the target reference — plus new tests for the precondition
failure paths (dirty teardown, target still active, target's branch already
attached elsewhere for any reason). This is a genuine engine-level feature,
not a one-line change; I'd estimate low hundreds of lines across
`surface.rs` and `engine.rs` plus proportionate test coverage, but I have
not scoped the CLI/API/journal-schema surface closely enough to give a
confident total.

**Argument for:** it is the only mechanism that satisfies no-mistakes'
actual assumption (verified in §4) without inventing a reconciliation step
sergeant does not have authority to perform per its own "never improvise"
rule. It reuses a git-level operation (`add_worktree_from` with
`create_branch: false`) sergeant's own code already runs in `rematerialize`,
so the failure modes (stale registration, missing directory) are already
handled patterns, not new ones.

**Strongest argument against:** it makes gate dispatch timing a hard
constraint on the engine, not just a scheduling nicety — a gate Work
*cannot* be started while the target Work's surface still holds the branch,
and "the target's teardown was clean" is a new kind of precondition no
other Work-dispatch path in this engine currently checks. If Captain (or
whatever dispatches the gate Work) gets this wrong, the failure is not a
graceful `blocked` state today — it's whatever `git worktree add` returns,
surfaced however the new code chooses to surface it. This is exactly the
"sequencing constraint the proposal never states" the critic flagged, and
Mechanism A does not remove that constraint — it just makes it the explicit
price of correctness rather than an unstated assumption. Anyone
implementing this must design the fail-closed behavior for a non-clean
target teardown before dispatch logic is trustworthy, and that design does
not exist yet.

### Mechanism A′ — forced co-located worktree (tested, rejected)

`git worktree add --force <path> <branch>` while the target Work's own
worktree is still live. Verified working in §2. Rejected as a
recommendation: it produces two simultaneously-checked-out worktrees on one
branch with no mechanism keeping them consistent, is the specific case
git's own default behavior refuses to allow, and would let a gate Work run
concurrently with (rather than strictly after) the Work it is reviewing —
directly undermining the "the gate reviews finished output" framing ADR
0005 and §5.1 use throughout. Not designed further here because there is no
argument for it over Mechanism A once Mechanism A's sequencing is accepted;
its only "advantage" is not waiting for teardown, which is not a real
advantage given what it costs.

### Mechanism B — review a copy (the proposal's other named option, confirmed broken)

Cut a new branch from the target's tip and review that. Confirmed via §4:
`axi sync --recover` fast-forwards the branch checked out in the worktree
it is run against — a copy branch receiving pipeline fix commits never
moves `sergeant/<target-work-id>`, so the real branch ships without the
fixes the gate produced. This is the failure the refuter already
established at error severity; nothing found here weakens that. Not
recommended.

### Mechanism C — fold gating into the producing Work's own pipeline (no second Work)

Considered as a candidate "third path": if the *same* Work that produced
the code also ran its own gate stage before reaching a terminal state, its
surface's branch would never need to be shared with anything, because
there would be only one Work and one surface. This would trivially dissolve
the whole binding question.

Not recommended, and not designed further, because it conflicts with what
ADR 0005 and §5.1 actually describe, not just with how they could be read:
§5.1 frames the gate Work as "grading **another** Work's output," and
records as a consequence to watch "the gate Work reviewing a branch is a
Work grading another Work's output; the independence that makes the review
valuable must not quietly become self-review" (§5.1, also cross-referenced
at §8.2). The refuter checked this exact reading and found nothing in the
document supporting it (`refuters/invariants.md`, "Does the proposal's own
text supply an escape hatch the critic missed?"). Folding gating into the
same Work would answer a question the proposal did not ask — the owner's
ruling was that gating becomes *a dispatched Work* reviewing another Work's
output, and re-reading that as "no second Work" is closer to relitigating
ADR 0005 than to answering §8.6. Named here because the task asked whether
a third path exists; not adopted.

### Mechanism D — detached-HEAD review copy, hybrid

Materialize the gate Work's surface as a detached checkout of the target
branch's tip (verified in §2 to coexist safely with a still-live worktree
on that branch, no exclusivity conflict). No-mistakes' read-only stages
(review, test, lint) could run against it. But the moment any stage needs
to commit a fix — which `40-drive-gates`' auto-fix action explicitly allows
the pipeline to do — that commit has nowhere to land: a detached HEAD is
not on any branch, so nothing advances `sergeant/<target-work-id>`. This
degrades to Mechanism B's problem (a wrong artifact) the first time an
auto-fix finding actually fires, which `docs/adr/0005-gating-becomes-a-dispatched-work.md` records as expected to happen regularly ("four real defects,"
"a regression its own fix had introduced," from the same day). Not
recommended as a general mechanism; possibly relevant to a future
read-only-only gate variant, but that is not what `validate-and-ship`'s
`40-drive-gates` stage currently is.

## Recommendation

**Mechanism A** (sequenced branch takeover): dispatch the gate Work only
after the target Work is terminal and its surface has torn down clean, then
materialize the gate Work's surface by attaching to the existing
`sergeant/<target-work-id>` branch rather than minting a new one.

It is the only mechanism that satisfies no-mistakes' verified custody
assumption without inventing an unauthorized reconciliation step, and it
extends a git operation (`create_branch: false` attach) sergeant's own code
already performs in a different context (`rematerialize`), rather than
introducing a wholly new one. Its cost is real and specific, not vague: a
new precondition the engine must check and fail closed on, and submission
plumbing that does not exist today to carry a target reference into
`SurfacePlan`. The strongest objection is that this makes gate-dispatch
timing a hard engine-level constraint rather than a convention — but that
constraint is implicit in ADR 0005's own framing already ("grading another
Work's output" presupposes the output exists and is no longer being
written to), so Mechanism A makes an already-implied ordering explicit and
enforceable instead of adding a new one.

## What it would take to implement, sized honestly

Not a small follow-up. At minimum:

1. A precondition check ("is `<target-work-id>` terminal with a clean
   surface teardown") — new engine-level logic, reading journaled
   `surface.torn_down` state that nothing currently queries for this
   purpose.
2. A `materialize`-adjacent function (or a `SurfacePlan` variant) that
   attaches to a caller-specified existing branch instead of minting
   `work_branch(work_id)` — bounded in `src/runtime/surface.rs`, reusing
   `add_worktree_from(..., create_branch: false)`, but needs its own
   `RepositoryBinding` provenance shape (see Mechanism A's cost notes) and
   its own tests for the failure paths git actually has (branch still
   attached elsewhere, branch missing, worktree path collision).
3. A way to submit "this Work reviews `<target-work-id>`" — new field
   somewhere in `SubmitContext`/`StartPlan`, plus whatever CLI/API surface
   Captain would use to dispatch it. Not scoped here.
4. Explicit fail-closed behavior for every precondition failure (target
   not terminal, target terminal but surface retained-dirty, target's
   branch already attached to something for an unrelated reason) — none of
   these paths are designed, only named as needing a design.
5. Findings-to-Work schema and the `ask-user`/`auto-fix`/`no-op` routing
   ADR 0005 itself lists as a separate open question — orthogonal to
   binding but landing in the same Work, so likely built together.

I'd size the surface/engine core of this (items 1-2) as a real but
contained engine change; items 3-4 are where the actual uncertainty is,
because they require product decisions (what does Captain's dispatch call
look like, what happens when a target's teardown is dirty) that this
investigation was not asked to make and did not make.

## What I could not determine

- **Whether Captain's dispatch mechanism (however §5.1's "Sgt executes"
  becomes concrete) can even guarantee the sequencing Mechanism A needs.**
  I confirmed the *engine's* own retirement ordering guarantees a Work's
  surface tears down before... nothing else about that Work happens (it's
  terminal). But whether whatever dispatches a gate Work will reliably wait
  for that teardown to be reported before submitting the gate Work is a
  question about the not-yet-designed dispatch mechanism, not about
  `surface.rs`. Named as open, not guessed.
- **What should happen when the target Work's teardown is not clean**
  (`RetainedDirty`/`RetainedError`). I traced that this blocks Mechanism A
  mechanically (git refuses) but did not design the remediation — block,
  escalate to the user, or route through the target's own retry path are
  all plausible and none is chosen here.
- **Whether a `RepositoryBinding` that records "attached, not cut" needs a
  schema change to existing journaled event payloads**, or can reuse
  `base_branch`/`base_sha` with a documented reinterpretation. I flagged
  the ambiguity but did not resolve it — it depends on how strictly
  `work show`/`work transcript` and the analytics projection
  (`src/runtime/analytics.rs`) currently rely on those fields meaning
  "cut from," which I did not audit exhaustively.
- **Multi-repository gate Works.** Everything above was verified against
  the single-repository case. A gate Work reviewing a multi-repo target
  Work would need every one of that target's bindings to have torn down
  clean before any of them could be attached to — not measured or reasoned
  through here.
