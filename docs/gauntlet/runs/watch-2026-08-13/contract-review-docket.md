### buildability:watch-r9-teardown-race — error

**Claim.** R-WATCH-9's Pin ('a test asserts the notice's snapshot deep-equals the endpoint body at emission time') is not actually testable as specified for completed/canceled/failed notices delivered via a live state_transition (or an already-terminal current_state whose helper only polled `work.state`): work_view's `output` and `teardown` fields are populated by a SEPARATE, asynchronous cascade step that lands strictly after the state-transition event broadcasts, so any comparison GET issued after the fact (which is the only way an external test process can compare) races that cascade and will be flaky.

**Evidence.** src/api.rs:1489-1536 work_view's `teardown`/`output` fields; src/api.rs:1438-1441 output_pointer returns None until `run.teardown` is Some; src/runtime/engine.rs:2187-2201 BackendSignal::Failed and :2203-2221 StageCompleted both call `self.teardown_next(...)` AFTER the KIND_WORK_FAILED/COMPLETED transition is already committed (and broadcast — src/api.rs:180 `self.events_tx.send(event)` fires per-event inside `commit`, not once at the end of `crank`); src/runtime/engine.rs:3691-3705 teardown_next returns a `Next::Surface` effect that crank (src/api.rs:489-538) performs on a LATER loop iteration, with the guard dropped and a real blocking git operation in between (engine.rs:3710-3729's own doc comment: '`work.completed` and its trailing `surface.torn_down` are two adjacent appends' — the exact L6 hazard class this repo already names elsewhere). A watch client subscribed via SSE sees `work.completed`/`work.failed` the instant it's appended and can complete its own GET before that later teardown iteration lands, so its snapshot legitimately has `output`/`teardown: null` — but any SEPARATE query issued moments later by a test (the only mechanism available to check 'deep-equals... at emission time' from outside the watch process) will very plausibly see the fully-populated fields instead, causing an intermittent mismatch. This is precisely the flaky-pin class LESSONS.md L7 warns about ('single-run green is not a gate... repeated-run checks are part of gate verification') and that TH-05's class (cited by R-WATCH-6 itself) already names for this same contract.

**Evidence.** R-WATCH-6 (docs/gauntlet/contracts/WATCH.md:107-121) says the hold 'extend[s]' fake.rs's `Gate` env-knob pattern 'to the client process, where fake.rs's in-process Gate cannot reach' — but the cited precedent's own OBSERVER-side wait is explicitly bounded: `fn wait_for_waiting(&self, n: usize, timeout: Duration) -> bool` (src/backend/fake.rs:337-354) returns false on timeout rather than blocking indefinitely.
