# M3 Contract — Work Surfaces, Workflow Engine, Routing, Fake Backend

**Outcome.** A submitted Work can actually execute: the daemon materializes an
isolated git-worktree surface, binds a staged workflow, routes to a backend
through the origin-affinity precedence chain, drives the stages through a
deterministic in-process fake backend, and completes — all observable through
the M2 API/CLI and all recorded in the M1 journal. This is where "work state ≠
process state" becomes testable.

**In scope** (proposal §9, §11–§14; fake backend per §37).

- `domain/workspace.rs` — single-repo zero-config discovery
  (`git rev-parse --show-toplevel`); optional multi-repo workspace via a
  checked-in `sergeant.toml` (§9 shape, D1 naming): workspace name +
  `[[repository]]` entries (name, path). Topology only; never transient state.
- `runtime/surface.rs` — work surface materialization per §11: per-repository
  binding records (source repo, base branch, base SHA, worktree path, work
  branch, current HEAD); worktrees created with the installed git CLI under the
  daemon's data dir (never inside the source checkout); teardown on terminal
  state retains the branch, removes the worktree; a dirty or missing worktree at
  teardown is recorded, not silently destroyed (fail closed).
- `domain/workflow.rs` + `runtime/` — workflow as versioned filesystem content
  per §12: `.sergeant/workflows/<name>/workflow.toml` + ordered stage dirs with
  `CONTEXT.md`. Engine supports §12's verbs only: ordered stages, explicit
  entry/completion, waiting, needs_input, blocked, retry, failure,
  cancellation. Stage state is journal events; Work.state and current stage are
  orthogonal (§10). Stage completion happens only via explicit signals from the
  backend adapter or API — never inferred from process liveness (§25).
  A built-in minimal `software-change` workflow ships as embedded default.
- `runtime/router.rs` — §13 precedence exactly: explicit backend → origin
  affinity → workspace default → global default → fail with available options.
  Origin metadata on submit (`origin.client`). Never silently substitute an
  unavailable backend.
- `domain/` profiles — §14: named launch configuration (backend, executable,
  env overrides, default model, options). No credentials, ever.
- `backend/mod.rs` — the §15 contract trait, minimum viable surface for M3:
  probe, start, send, observe, stop + capability flags. (subscribe/history/
  interrupt/resume arrive in M4 with real backends; trait is extended then —
  do not pre-declare unimplementable methods.)
- `backend/fake.rs` — deterministic in-process backend: scriptable responses
  (complete stage, request input, block, fail, hang), no external processes.
  This is the §37 deterministic-core instrument.
- API/CLI additions: `POST /v1/work/{id}/input` (answer needs_input),
  work show includes stage + surface + execution state; `sgt respond <id>`.

**Acceptance tests.**

1. Zero-config: in a temp git repo, submit → surface materialized as a real
   worktree on a work branch from the current HEAD; binding record complete;
   base SHA correct.
2. Multi-repo: `sergeant.toml` with two repos → one surface, two worktree
   bindings.
3. Full run: submit against fake backend scripted to complete all stages →
   Work reaches `completed`; journal shows stage entry/completion events in
   order; worktree cleaned up; branch retained.
4. needs_input: fake backend requests input → Work `needs_input`; API input →
   run resumes → completes. Input to a Work not waiting → structured error.
5. Failure: fake backend fails a stage → Work `failed` with recorded reason;
   retry verb re-enters the failed stage, succeeds on scripted second attempt.
6. Cancellation mid-stage → `canceled`; surface teardown recorded; no zombie
   state; work state ≠ process state proven: fake backend still "running" its
   hang script while Work is already `canceled` — the engine never infers
   work state from the backend's process state.
7. Routing: precedence chain covered — explicit flag beats origin affinity
   beats workspace default beats global default; no backend resolvable →
   structured failure listing options.
8. Daemon restart mid-run: on recovery, in-flight Work is re-observed via the
   backend contract; unambiguous states resume; ambiguous states fail closed
   to `blocked` with evidence (§25).

**Non-goals.** Real backends (M4), DuckDB/graph/OTel (M5), TUI/HTML (M6),
generalized DAG scheduling (§4 explicitly), treehouse-style worktree pooling
(R1 — Sergeant evidence says useful, not needed for the contract proof).

**Unknowns.**

- Worktree teardown while a fake "process" is scripted-hanging: exact teardown
  ordering vs. execution retirement — resolve during build, record the rung.
- Whether stage CONTEXT.md content is consumed by anything before M4 (likely
  carried but unread; that's fine — procedure is data, §40).
