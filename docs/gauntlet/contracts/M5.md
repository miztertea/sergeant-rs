# M5 Contract — DuckDB Projection, Graph, OTel

**Outcome.** The trajectory becomes queryable and observable: an embedded
DuckDB analytical projection rebuilt entirely from the journal, a derived
graph projection with per-edge source provenance, and OTel trace/metric
export — all three strictly **disposable projections** (§40): delete any of
them and nothing is lost; the journal remains the only truth.

**In scope** (proposal §21 "DuckDB", §22, §23, §28; §8's graph endpoints).

- DuckDB (§21–22): embedded via the Rust client (the proposal names it —
  R5), file at `<data-dir>/projections/sergeant.duckdb` (D1 naming). Only
  the daemon touches it; clients ask the API. Populated by folding journal
  events — either incrementally on append or by rebuild; **rebuild from
  scratch is the contract**: delete the file, daemon rebuilds, identical
  query results (§21's replay diagram). Tables: the §22 list *as far as the
  journal actually carries the data today* (events, work, executions,
  stages, tool_calls, usage, repositories, graph_nodes, graph_edges, plus
  messages if conversation events suffice) — an empty speculative table is
  an R1 finding, not completeness.
- Graph (§23): derived temporal projection, not a graph database. Nodes and
  edges from the §23 representative sets as instantiable from real journal
  data; **every derived edge records its source event seq** (§23's
  inspectability rule). Served via `GET /v1/graph/work/{id}` (neighborhood,
  §8); `sgt work show --graph` or similar minimal CLI rendering.
- OTel (§28): `tracing` spans already exist; add opentelemetry export
  (OTLP) behind config, **off by default** — internal events remain the
  truth, OTel is an export projection. Span shape per §28's work/stage/
  execution/tool nesting where the engine already has the structure. The
  §28 metric list: implement the counters/histograms whose inputs exist
  (work/execution/stage durations, waits, backend failures, token totals
  from usage events, journal append timing). Verification without a real
  collector: in-memory/stdout exporter asserted in tests; OTLP wiring
  smoke-tested against a local listener if trivial, else documented-not-
  measured and off.

**Acceptance tests.**

1. Rebuild determinism: run real work (fake backend) → daemon populates
   DuckDB → delete the .duckdb file → restart/rebuild → the §22 canned
   queries return identical results (row-for-row).
2. One owner: the API answers analytics/graph queries; nothing outside
   `daemon`/`runtime` opens the DuckDB file (enforced by module visibility;
   probed by grep-level test or code review — critics verify).
3. Graph provenance: for a completed work, every edge in
   `/v1/graph/work/{id}` carries a `source_seq` that resolves to a real
   journal event whose content justifies the edge.
4. Projection disposability: deleting projections/ mid-flight (daemon
   stopped) loses nothing — journal replay restores; work state unaffected.
5. OTel: with the exporter enabled in test config, a fake-backend run emits
   the §28 span tree (work → stage → execution.turn) and the implemented
   metrics; with it disabled (default), zero exporter machinery runs.
6. Analytics smoke: at least three of §22's example questions answerable
   via the daemon (e.g. time blocked per work, tool-call counts preceding
   failure, backend retry counts) — as API/CLI surface or documented canned
   queries, minimal rendering (R1 on dashboards; M6 owns presentation).

**Non-goals.** Graph database engines (§23 explicitly); direct client
access to DuckDB; OTel on by default; dashboards/HTML (M6); snapshot
adoption in the daemon path (B1 stays parked unless rebuild cost measured
here demands it — if so, B1's trigger fires and the ledger records it).

**Unknowns.**

- The duckdb crate's bundled-build cost in this container (compile time and
  disk) — measure first; if prohibitive, the fallback decision (feature
  gate, or a leaner embedded store honoring the same rebuild contract) is
  an adjudication with rungs, not a silent swap.
- Incremental-vs-rebuild population: rebuild is the contract; incremental
  is an optimization added only if rebuild latency on realistic journals
  measures as annoying (numbers in the build report).
- OTLP smoke feasibility offline.

**Dependency budget.** duckdb (R5, proposal-named), opentelemetry +
opentelemetry-otlp + tracing-opentelemetry (R5, §28-named), off-by-default.
Anything else rung-logged.

**Gauntlet depth.** Economy cadence: build + round-1 panel + batched
refuters in one workflow (builder Opus high; invariants critic Fable high —
disposability and one-owner are the §40 principles under test; others Opus
medium), checkpoint gate, lean round 2, adjudication. All prompts carry
register-first, probe hygiene, exploration budget, rung logging, L6/L7/L8.
