# M6 Contract — TUI, HTML Dashboard, Doctor, E2E Demo

**Outcome.** The P0 slice closes: the daemon's state becomes visible to
humans through a terminal UI and an embedded web dashboard, `sgt doctor`
diagnoses an installation, and the §39 first-user-experience walkthrough runs
end-to-end as an executable script. Every client is a projection of the same
API — nothing in this milestone may touch daemon internals, storage, or the
journal directly (§7/§30: "If the TUI needs a private shortcut, the API is
incomplete" — that sentence is this milestone's invariants axis).

**In scope** (proposal §29, §30, §31's `doctor`, §39; §7's clients-are-equal
rule; §34's ratatui/crossterm).

- `tui.rs` — `sgt` with no subcommand opens the TUI (§30): a fleet screen
  (work list with states, live via SSE) and a work detail screen (stage,
  execution, surface bindings, recent events tail). ratatui + crossterm
  (§34-named, R5). Exclusively through the loopback API with the descriptor
  token; auto-spawn applies as for any client. Read-only in v1 except
  cancel/respond keybinds if trivially cheap (R1 otherwise — record the
  call). Quit cleanly; never leave the terminal raw.
- `web.rs` — §29: the daemon serves an embedded, server-rendered HTML
  dashboard (assets via `include_str!`/`include_bytes!` — the binary stays
  self-contained; no Node, no CDN). Screens: Fleet and Work detail (intent,
  workflow/stage, surface, execution + native session identity,
  conversation/tool activity from normalized events, state transitions,
  usage). Live updates via EventSource on the existing SSE endpoint. Auth:
  the bearer token, delivered by a `sgt web` command that prints/opens the
  tokenized URL (localhost-only binding is already the surface; document the
  token-in-URL tradeoff and its rung).
- `cli.rs` — `sgt doctor` (§31): checks git presence/version, claude CLI
  presence + version-gate verdict, data dir writable + journal opens and
  validates, projection rebuild health, daemon liveness/descriptor state.
  Human + `--json`; exit code reflects health; each check names its remedy.
- §39 demo — `scripts/demo.sh`: in a temp git repo, drives the full loop
  with the fake backend deterministically: submit → surface → stages →
  needs_input → respond → completed → retire, printing at each step what
  happened and where the evidence lives (journal path, blob refs, analytics
  query, graph endpoint, dashboard URL). Exit 0 = the walkthrough holds.
  An optional `--real-claude` flag runs the same shape through the real
  adapter behind `SERGEANT_CLAUDE_TESTS=1` budget discipline.

**Acceptance tests.**

1. TUI data/render: against a live daemon with seeded work, the fleet and
   detail screens render the contracted fields (ratatui `TestBackend`
   snapshot-ish assertions on content, not pixels); SSE-driven update
   reflected in a re-render; TUI module imports nothing from
   daemon/runtime/storage internals (API types only — structural check).
2. Dashboard: fetching Fleet and Work-detail pages over HTTP with the token
   returns HTML containing the seeded work's real data; without token →
   401; assets embedded (no filesystem reads at serve time — probe: serve
   from a binary run in an empty cwd).
3. Doctor: healthy env → exit 0 with all checks green; broken data dir and
   absent-claude each produce the named failing check, nonzero exit, and a
   remedy line; `--json` is stable.
4. Demo: `scripts/demo.sh` exits 0 in a clean temp environment and its
   printed evidence pointers resolve (journal exists, analytics answers,
   graph endpoint 200s).
5. Clients-are-equal: one structural test proving tui.rs and web.rs reach
   state only via HTTP types (no `use crate::runtime::…`/`daemon::…` except
   the API client surface — token-scan style per M5's t2 pattern).

**Non-goals.** Charts/visualizations beyond text and lists; a graph
renderer (the JSON endpoint is the deliverable; drawing it is post-P0);
MCP (§38 defers it past API stability); auth schemes beyond the existing
bearer token; TUI feature-completeness (fleet + detail is the contract);
OpenCode/Prime (D3/D6).

**Unknowns.**

- TUI testing ergonomics with ratatui TestBackend — **resolved (round 1):**
  content assertions did not prove brittle and are the primary instrument;
  the view-model layer is unit tested too, not merely as a fallback — see
  the "TUI test approach" note atop `tests/m6_surfaces.rs`.
- Whether `sgt web` should also work daemon-less (spawn like other client
  commands) — **resolved:** yes, via the shared auto-spawn path (default
  held; see `ensure_daemon` in `src/cli.rs`).
- Token-in-URL for the dashboard: acceptable for loopback P0; the rung log
  records the tradeoff and the post-P0 alternative (cookie handoff).

**Dependency budget.** ratatui + crossterm (§34-named, R5). Nothing else
without rung-logged justification (the dashboard is server-rendered strings
— no template engine unless string formatting demonstrably fails, R1).

**Close-out (after the gauntlet, before the final gate).** This milestone
ends the P0: the MARK & LOG includes a prototype close-out ledger entry
(scorecard totals across M0–M6, deviations D1–D7 summarized, backlog
disposition, LESSONS index), a README update reflecting real usage, and a
PR body refresh with the full summary — the PR is the deliverable's front
door.

**Gauntlet depth.** Economy cadence: build + round-1 panel + batched
refuters in one workflow (builder Opus high; invariants critic Fable high on
the clients-are-equal rule; others Opus medium), checkpoint gate, lean round
2, adjudication. All prompts carry register-first (D1–D7), probe hygiene,
exploration budget, rung logging, L6–L9.
