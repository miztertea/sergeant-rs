# M2 Contract — Daemon, API, CLI, Idempotency

**Outcome.** The one-owner architecture becomes real: a single long-lived daemon
process is the only thing that mutates runtime state, every mutation flows
through the M1 journal, and clients — starting with the CLI — consume one
loopback HTTP/JSON + SSE surface. Work can be submitted, listed, inspected, and
canceled durably across daemon restarts, with exact-once command semantics.

**In scope** (proposal §6–§8, §10, §26; CLI per §31 subset).

- `daemon.rs` — one process owns the journal and projection. On start: acquire
  an exclusive daemon lock in the data dir (second daemon fails closed), write a
  runtime descriptor (endpoint, PID, API revision, random bearer token) with
  owner-only file permissions, bind `127.0.0.1` on an ephemeral port, serve
  until shutdown. Descriptor removed on clean shutdown.
- `api.rs` — axum. Routes (§8 subset): `POST /v1/work`, `GET /v1/work`,
  `GET /v1/work/{id}`, `POST /v1/work/{id}/cancel`, `GET /v1/events`
  (history, from a given seq), `GET /v1/events/stream` (SSE, live tail with
  `Last-Event-ID`-style resume by seq), `GET /healthz` (unauthenticated),
  `GET /v1/system` (version, API revision, data dir). All non-healthz routes
  require the bearer token. Errors are structured JSON.
- `domain/work.rs` — Work record per §10 (id, workspace, intent, targeted
  repositories, workflow, state, created_by, created_at) and the §10 state set
  (`pending, active, waiting, needs_input, blocked, completed, failed,
  canceled`). In M2 only the transitions that exist without a workflow engine
  are reachable: submit → `pending`, cancel → `canceled`. The state machine
  rejects illegal transitions (fail closed); later milestones add legal ones.
- **Events, not writes.** API handlers append events (`work.submitted`,
  `work.canceled`, `command.accepted`/`command.rejected`, daemon lifecycle
  events) and read from the projection. The M1 demo projection is evolved into
  the real Work registry reducer — this evolution is explicitly contracted
  (M1's counts/work-id projection was scaffolding for determinism proofs).
- **Idempotency (§26).** Every mutation carries a client-supplied `command_id`
  (ULID). The daemon records command acceptance and result in the journal;
  a repeated `command_id` returns the recorded result without re-executing —
  including across a daemon restart.
- `cli.rs` — `sgt daemon` (run foreground); `sgt status` (daemon health +
  counts); `sgt run "<intent>"` (submit work; workflow/backend fields recorded
  for M3/M4 but not executed); `sgt work list`, `sgt work show <id>`,
  `sgt cancel <id>`; global `--json` for machine output. Client auto-spawns the
  daemon (detached child, wait for descriptor + healthz) when the descriptor is
  missing; a descriptor whose endpoint refuses connection and whose PID is dead
  is stale — replace it; PID alive but endpoint unresponsive is ambiguous —
  fail closed with a diagnostic rather than spawning a second daemon.
- Dependencies added: axum, tower, reqwest (client, rustls). Dev-deps as needed.

**Acceptance tests.**

1. Daemon start writes descriptor (owner-only permissions, valid JSON,
   loopback endpoint); `/healthz` responds; clean shutdown removes descriptor.
2. Missing/wrong bearer token → 401 on `/v1/*`; correct token → 200.
3. Submit via API → visible in list/show as `pending`; journal contains
   `work.submitted`; daemon restart (same data dir) → work still listed
   (replayed, not cached).
4. Same `command_id` submitted twice → one Work record, byte-identical result;
   also true when the duplicate arrives after a daemon restart.
5. Cancel → `canceled`; duplicate cancel idempotent; cancel of unknown id →
   structured error; `canceled → pending` transition impossible.
6. SSE: client connected to `/v1/events/stream` receives an event appended
   after connect; a client resuming from seq N receives exactly the events
   after N.
7. CLI end-to-end (spawned binary): `sgt run` with no daemon running
   auto-spawns one, submits, and `sgt work list --json` shows it; second
   daemon start against the same data dir fails closed.
8. Both daemons race: two concurrent auto-spawn attempts yield exactly one
   surviving daemon and both clients complete their command.

**Non-goals.** Worktrees, workflow stages, routing, profiles (M3); backends
(M4); `respond`/`resume`/`retry` routes (arrive with the workflow engine);
DuckDB/OTel (M5); TUI/HTML (M6); any remote binding.

**Unknowns.**

- Detached-daemon spawn semantics in this container (process groups, no
  systemd): resolved by the acceptance tests themselves — test 7/8 measure it.
- SSE keep-alive cadence: pick a value, note it; nothing depends on it yet.

and idempotency live here).
