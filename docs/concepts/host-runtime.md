# Host runtime and estates

There is one long-lived Sergeant daemon per user installation, not one per estate. It owns a host runtime root (`--data-dir` / `SGT_DATA_DIR` / the platform default) holding the journal, the DuckDB projection, and the daemon's own descriptor, lock, and token. On Linux/WSL the installer registers it as a systemd user service; on macOS, a LaunchAgent. Either way a native per-user service manager supervises the daemon process — Sergeant does not implement its own supervisor, and does not enable systemd lingering on its own initiative. `sgt daemon stop` stops the whole daemon, every admitted estate at once, and says so.

A freshly started daemon is bound to zero estates. It admits an estate the first time a request addresses one — `sgt run`, `sgt repo`, or any other estate-scoped verb naming an exact root, either because the working directory is that root or because `-C <estate-root>` names it explicitly. Admission validates the manifest at that exact path (no upward search, no Git inference) and records the root in an in-memory registry the daemon rebuilds from requests; nothing here is persisted across a restart, and nothing grants estate status beyond passing that check. A second estate reuses the running daemon rather than starting another. A handful of verbs — `sgt tui`, `status`, `work show`/`list`/`transcript`, `watch`, `analytics` — read from any directory once a daemon exists; a verb that creates Work or mutates an estate declaration still requires exact addressing, and outside an estate without `-C` it refuses rather than guessing.

Estate-local material — `sergeant.toml`, `repos/<name>` mounts, `.sergeant/workflows/`, Work surfaces — stays exactly where it always did. Only the journal, the projection, and the daemon's own runtime state moved to the host root; a repository mount or a Work surface never did, and moving them was explicitly out of scope for this change.

## What the manifest's storage-path authority still protects

Before the host daemon, the manifest's `[estate] data_dir` deprecated a global-collision hazard: if a machine-global path outranked the estate, every estate on that machine would share one journal, one blob store, and one exclusive lock, and one estate's Work could reference another's repositories by accident. The host runtime makes that sharing deliberate instead of accidental — one journal, distinguished by each event's own canonical estate-root coordinate, admitted through the same exact-root check that used to gate a single estate's own data dir. What the old collision concern actually protected — that a request is never served for an estate nobody validated, and that one estate's Work never silently reads as another's — survives intact; what changed is that the daemon now serves many validated estates from one root by design, not by accident. `[estate] data_dir` itself is deprecated at cutover: the journal and projection it used to place no longer have a per-estate home to place, though `surfaces_dir` is untouched and Work surfaces stay estate-local as before.

## The no-spawn set, re-derived

Observation must not materialize the thing observed. `sgt doctor`, `sgt watch`, and `sgt daemon stop` never spawn a daemon just to have something to inspect, and neither do `status`, `work show`/`list`/`transcript`, `analytics`, or the TUI — only a verb that actually mutates durable state (`run`, `respond`, `retry`, `extend`, `cancel`) starts one on demand. That rule predates the host daemon and does not change with it: a daemon bound to zero estates is the ordinary starting state now, not a special case, so a bare `sgt status` on a fresh installation still answers "no daemon running" rather than starting one to report on. What did change is what a daemon being *bound* to an estate even means: before, one process served exactly one estate, and a client whose estate didn't match the daemon's got a hard mismatch refusal. Under the host runtime a daemon serving an estate it was not started from is the ordinary case, so that mismatch refusal is retired; what replaces it is a request-shaped taxonomy — the addressed root is not an estate at all, admission failed for a reason of its own (an unreliable filesystem), or an estate-scoped operation named no estate to act on — because the property worth keeping was never "one process, one estate," it was "never serve a request for an estate nobody validated."

## Decisions

| ID | Decision |
|---|---|
| D1 | An estate's coordinate is its canonical exact root, carried on every estate-bound event — never a display name, never a minted UUID. |
| D2 | The host data root resolves the same way it always did: `--data-dir`, then `SGT_DATA_DIR`, then the platform convention (XDG on Linux, Application Support on macOS). |
| D3 | The runtime descriptor (schema `sergeant.runtime/v3`) carries no estate set — admitted estates are dynamic daemon state served over the API, not baked into a file written once at startup. An older descriptor schema is refused, never silently accepted. |
| D4 | Every wire request that means an estate names it explicitly with its canonical root; the daemon validates by admission, never by trusting what the caller sent. |
| D5 | `sgt daemon stop` stops the host daemon — every admitted estate — and says so. Per-estate pause or drain is not part of this. |
| D6 | The fleet endpoint returns every admitted estate's Work; the TUI filters client-side. The live event stream accepts an optional estate filter, so `sgt watch` run inside an estate keeps meaning that estate alone — a host-wide watch has to ask for it. |
| D7 | Retention is partitioned per estate, but the blob-reference scan that garbage collection depends on stays journal-wide regardless — a per-estate retention decision must never be able to condemn another estate's still-live blobs. |
| D8 | One bearer token authorizes every admitted estate on the daemon. This is a real widening of blast radius from the one-estate world, accepted deliberately under the single-user trust model this installation assumes — a leaked token now reaches every estate the daemon has admitted, not one. |
| D9 | The manifest's `[estate] data_dir` key is deprecated at cutover — the journal and projection it used to place have no per-estate home left to place. `sgt doctor` warns on a manifest that still declares it. `surfaces_dir` is untouched. |
| D10 | The engine resolves an estate per submission, not once per process — the old process-wide `estate_root` binding is gone, not merely unused, and recovery resolves each Work's estate from its own journaled coordinate rather than from whatever the process happened to be bound to. |

See [estates and Git surfaces](estates-and-git.md) for the estate boundary itself, and [data, environment, and telemetry](../reference/runtime.md) for the exact resolution order and environment variables.
